================================================================================
1. SYSTEM OVERVIEW
================================================================================

What the application does
-------------------------
MediCare is a single-page web application for booking medical appointments.
A patient (there is a single implicit patient profile, no login) can:

  - Browse a list of doctors
  - Search doctors by name and filter them by specialty
  - Open a doctor's detail page (working days, time slots, fees, contacts)
  - Book an appointment with a selected doctor (patient details, date, time,
    optional note)
  - View all of their appointments ("My appointments")
  - Edit / reschedule an existing appointment
  - Cancel (delete) an appointment, with a confirmation dialog
  - Save a patient profile (name, email, phone) that pre-fills the booking form

Main purpose
------------
This is the final individual project of the React Summer Training at ITI. Its
purpose is to demonstrate a complete React SPA with routing, global state,
REST CRUD communication, form validation, and loading/error/empty state
handling.

Main user workflow
------------------
Home page (doctor list) -> search/filter -> doctor details -> book appointment
(form) -> redirected to My appointments -> optionally edit or cancel an
appointment. Patient contact details can be saved once on the Profile page and
are then re-used to pre-fill the booking form.

Overall architecture
--------------------
Classic single-page-application architecture with a clear layering:

  React UI (pages + reusable components)
      |
  React Router (createBrowserRouter, lazy-loaded routes)
      |
  Zustand store (patient profile only) + component-local state for everything else
      |
  Axios API service layer (src/services/api.js) — single axios instance
      |
  REST API (json-server, http://localhost:3001, reading/writing db.json)
      |
  Data storage: db.json file on disk (plus localStorage for the profile)

There is NO custom backend (no Node/Express, no ASP.NET, no Spring, no
Firebase/Supabase). The only "server" is json-server, a mock REST API.

3. FRONTEND ARCHITECTURE
================================================================================

Main folders
------------
  src/
    components/
      layout/       Layout, Navbar, Footer (shared page shell)
      doctors/      DoctorAvatar, DoctorCard, DoctorFilters, DoctorList
      appointments/ AppointmentCard, AppointmentForm, AppointmentStatus
      ui/           shadcn-style primitives: alert, badge, button, card,
                    dialog, input, label, select, skeleton, textarea, toast
    pages/          The 7 route-level pages
    routes/         router.jsx (route configuration)
    services/       api.js (Axios instance + API functions)
    stores/         useProfileStore.js (Zustand store)
    lib/            utils.js (cn helper)
  db.json           json-server data file (project root)
  dist/             Production build output (already built once; committed)

Entry chain
-----------
  index.html -> src/main.jsx (createRoot, StrictMode, imports index.css)
             -> src/App.jsx (ToastProvider wraps RouterProvider)
             -> src/routes/router.jsx (createBrowserRouter with lazy pages)

Pages and their responsibilities
--------------------------------
  src/pages/DoctorsPage.jsx (home, route "/")
    Fetches all doctors (GET /doctors). Owns the search text and the specialty
    filter as LOCAL state. Derives the specialty list and the filtered doctor
    list with useMemo. Renders DoctorFilters + DoctorList, plus loading
    skeleton, error alert with retry, and an empty-search state.

  src/pages/DoctorDetailsPage.jsx (route "/doctors/:id")
    Reads :id with useParams, fetches one doctor (GET /doctors/:id).
    Distinguishes 404 ("not-found") from other errors ("network"). Shows the
    doctor's full profile and a "Book Appointment" link to /book/:id.

  src/pages/BookAppointmentPage.jsx (routes "/book" and "/book/:doctorId")
    Fetches the doctor list, reads the patient profile from the Zustand store,
    and renders the shared AppointmentForm with defaultValues (profile values
    + preselected doctorId from the URL param). On submit, POSTs the
    appointment with status "scheduled", shows a toast and navigates to
    /appointments.

  src/pages/AppointmentsPage.jsx (route "/appointments")
    Fetches appointments AND doctors in parallel (Promise.all), builds a
    doctorById lookup map, sorts appointments newest-first, and renders one
    AppointmentCard per appointment. Owns the cancel flow: a "cancelTarget"
    state opens a confirmation Dialog; confirming issues
    DELETE /appointments/:id and removes the item from local state.

  src/pages/EditAppointmentPage.jsx (route "/appointments/:id/edit")
    Fetches the appointment (GET /appointments/:id) and the doctors in
    parallel. Handles 404 vs network errors. Renders the same AppointmentForm
    pre-filled with the appointment's current values. On submit, PUTs to
    /appointments/:id, shows a toast, and navigates to /appointments.

  src/pages/ProfilePage.jsx (route "/profile")
    React Hook Form with defaultValues taken from the Zustand profile store.
    On submit, writes the values back into the store (persisted to
    localStorage) and shows a toast. No API call at all.

  src/pages/NotFoundPage.jsx (catch-all "*")
    404 page with links back to the main pages.

Key components
--------------
  components/layout/Layout.jsx — Navbar + <Outlet/> + Footer, max-w-6xl
    container, flex column with min-h-svh.
  components/layout/Navbar.jsx — brand "MediCare", desktop NavLinks with
    active styling, mobile hamburger menu (local useState).
  components/doctors/DoctorFilters.jsx — CONTROLLED search input (value +
    onChange) and specialty select; useRef to re-focus the input when the
    clear (X) button is clicked.
  components/doctors/DoctorCard.jsx — one doctor card: avatar, name link to
    /doctors/:id, specialty badge, rating, description, working days, slot
    range, fee, "View details".
  components/doctors/DoctorAvatar.jsx — deterministic initials avatar: strips
    the "Dr." prefix, takes first letters of the first two name parts, and
    picks a background color from a 6-color palette by (id % 6). No images.
  components/appointments/AppointmentForm.jsx — THE shared form (see
    sections 8 and 9). Used by both BookAppointmentPage and EditAppointmentPage.
  components/appointments/AppointmentCard.jsx — appointment summary with
    doctor info (via a doctor prop), status badge, details, and Edit/Cancel
    actions.
  components/appointments/AppointmentStatus.jsx — colored status badge
    (scheduled = sky, completed = emerald, cancelled = rose).
  components/ui/toast.jsx — custom toast system (Context + portal + timers),
    max 3 toasts, auto-dismiss after 4 s, manual dismiss, closing animation.
  components/ui/dialog.jsx — minimal modal (portal to body, Escape/overlay
    close, body scroll lock). Used only for cancel confirmation.
  components/ui/alert.jsx — ErrorAlert banner with optional "Try again"
    retry button, used on every failed fetch.

Services
--------
  src/services/api.js — the ONLY place that talks to the backend. One shared
  axios instance plus 7 exported functions (full details in section 5). All
  pages import from here; no component calls axios directly.

Stores
------
  src/stores/useProfileStore.js — the ONLY Zustand store (details in
  section 10).

Routing
-------
  Declarative, file-based route config in src/routes/router.jsx with lazy()
  + Suspense code-splitting per page (details in section 4).

How components communicate
--------------------------
  - Parent -> child: props (e.g. doctors/search/onSearchChange into
    DoctorFilters; appointment/doctor/onCancel into AppointmentCard).
  - Child -> parent: callback props (onSearchChange, onSpecialtyChange,
    onCancel, onSubmit).
  - Cross-page/global: the Zustand profile store (ProfilePage writes it,
    BookAppointmentPage reads it).
  - Global UI feedback: the toast context (useToast()).
  - Server data: always fetched by the page component itself with
    useEffect + service functions — there is no shared data cache; each page
    re-fetches on mount.

How state is managed / data flow
--------------------------------
  1. Server data (doctors, appointments) is fetched per page in useEffect and
     kept in local useState (data + loading + error per page).
  2. Derived data (filtered lists, doctorById map, sorted appointments) is
     computed with useMemo from that local state.
  3. Mutations (create/update/delete) are optimistic-free: the request runs,
     a toast reports the result, and on success the user is redirected (the
     list page then re-fetches) — except delete, which also removes the item
     from local state directly.
  4. The only globally shared data is the patient profile (Zustand +
     localStorage persist).
  Unidirectional flow: UI event -> handler -> API call -> local state update /
  navigation -> re-render.

4. ROUTING
================================================================================

Configured in src/routes/router.jsx with createBrowserRouter and rendered by
RouterProvider in src/App.jsx. All pages are lazy-loaded with React.lazy and
wrapped in Suspense (a skeleton fallback, function delay()).

Router type note: createBrowserRouter uses the HTML5 History API. A prebuilt
dist/ exists, but there is no server-side fallback rewrite configured here —
deep links on a static host would need SPA fallback rewriting (see section 16).

Route table
-----------
  URL                       Component                Purpose
  ------------------------- ------------------------ ---------------------------
  /                         DoctorsPage (index)      Home: browse/search/filter
                            (lazy)                   doctors. Fetched via
                                                     GET /doctors.

  /doctors/:id              DoctorDetailsPage        Full profile of one
                            (lazy)                   doctor. :id is a dynamic
                                                     param read with
                                                     useParams. GET /doctors/:id.
                                                     404 from the API renders
                                                     a "Doctor not found" alert.

  /book                     BookAppointmentPage      Booking form with NO
                            (lazy)                   preselected doctor (the
                                                     doctor dropdown starts
                                                     empty).

  /book/:doctorId           BookAppointmentPage      Booking form with the
                            (lazy)                   doctor preselected from
                                                     the URL (:doctorId feeds
                                                     defaultValues.doctorId).

  /appointments             AppointmentsPage         "My appointments" list
                            (lazy)                   (GET /appointments +
                                                     GET /doctors), with
                                                     cancel (DELETE) and links
                                                     to edit.

  /appointments/:id/edit    EditAppointmentPage      Edit / reschedule one
                            (lazy)                   appointment. :id read with
                                                     useParams; GET
                                                     /appointments/:id, then
                                                     PUT /appointments/:id.

  /profile                  ProfilePage              Patient profile form
                            (lazy)                   (Zustand + localStorage,
                                                     no API).

  *  (anything else)        NotFoundPage             404 page with links to
                            (lazy)                   /, /appointments, /book.

All routes are children of the Layout route (path "/"), which renders the
Navbar/Footer shell and an <Outlet/> — so every page shares the same chrome.

Navigation flow
---------------
  DoctorCard name/"View details" -> /doctors/:id
  DoctorDetailsPage "Book Appointment" -> /book/:doctorId
  Navbar links -> / , /appointments , /profile
  AppointmentsPage "Book new" / empty state -> /book
  AppointmentCard "Edit / Reschedule" -> /appointments/:id/edit
  After successful create/update -> navigate('/appointments')
  EditAppointmentPage "Discard changes" -> navigate(-1) (history back)
  Back links on detail pages -> "/" or "/appointments"

5. API / DATA FLOW
================================================================================

Axios configuration (src/services/api.js)
-----------------------------------------
  const api = axios.create({
    baseURL: import.meta.env.VITE_API_URL || '/api',
    headers: { 'Content-Type': 'application/json' },
  })

  - Single shared instance for the whole app.
  - Base URL: the VITE_API_URL env var; default "/api". Configured via
    .env / .env.example (which ships with VITE_API_URL=/api).

Base URL resolution
-------------------
  In development the frontend calls "/api/...". The Vite dev server
  (vite.config.js, server.proxy) proxies /api -> http://localhost:3001 and
  strips the "/api" prefix (rewrite), so "/api/doctors" becomes
  "http://localhost:3001/doctors". This avoids CORS entirely.
  Alternatively, setting VITE_API_URL=http://localhost:3001 calls json-server
  directly — json-server then needs CORS enabled (it is not configured here).

API functions (all unwrap response.data via .then((r) => r.data))
-----------------------------------------------------------------
  Doctors:
    getDoctors()                    GET    /doctors
    getDoctorById(id)               GET    /doctors/:id

  Appointments:
    getAppointments()               GET    /appointments
    getAppointmentById(id)          GET    /appointments/:id
    createAppointment(appointment)  POST   /appointments
    updateAppointment(id, appt)     PUT    /appointments/:id   (full PUT)
    deleteAppointment(id)           DELETE /appointments/:id

  These cover every endpoint the app uses. json-server itself additionally
  supports PATCH and query/filter routes (e.g. /appointments?doctorId=1),
  but the application code does NOT use them. Not implemented in the app:
  doctor create/update/delete, any filtering done server-side (all filtering
  is client-side).

Request/response flow (example: booking)
----------------------------------------
  1. User submits AppointmentForm (React Hook Form validates first).
  2. BookAppointmentPage.onSubmit builds the payload:
       { ...values, doctorId: Number(values.doctorId), status: 'scheduled' }
     (the select returns the doctor id as a string, so it is coerced to a
      number to match db.json's doctor ids).
  3. createAppointment POSTs JSON to /api/appointments (proxied to
     http://localhost:3001/appointments).
  4. json-server appends the object to the "appointments" array in db.json,
     assigns the next numeric id, writes the file, and returns 201 + the
     created object.
  5. On success: toast('Appointment booked successfully.'),
     navigate('/appointments') — the list page re-fetches with
     GET /appointments.
  6. On failure: toast('Unable to book...', 'error') and the submit button
     is re-enabled.

Error handling
--------------
  - Fetch errors: each page's loader sets error state; the UI renders the
    ErrorAlert component ("Please check that the API server is running...")
    with a "Try again" button that re-runs the loader. If json-server is not
    running, the dev proxy returns a 500 and the user sees this state.
  - Distinguishing invalid IDs: DoctorDetailsPage and EditAppointmentPage
    inspect err.response?.status === 404 (json-server returns 404 for unknown
    ids) and render a dedicated "not found" message instead of the generic
    network error.
  - Mutation errors: toast with type 'error'; no retry mechanism for
    mutations (the user simply tries the action again).

Loading states
--------------
  - Route-level: Suspense fallback (PageFallback in router.jsx) while lazy
    chunks load — skeleton page layout.
  - Data-level: each page has a loading flag set true while fetching and
    renders purpose-built skeletons (DoctorListSkeleton, FormSkeleton,
    AppointmentsSkeleton, EditSkeleton) built from the Skeleton primitive.

Empty states
------------
  - Doctors: "No doctors found — try a different name or specialty" when the
    search/filter combination matches nothing.
  - Appointments: "No appointments yet — book your first appointment" with a
    link to /book.

Success feedback
---------------
  - Custom toast notifications (bottom-right, auto-dismiss 4 s, success /
    error / info icons) for every mutation outcome:
    booked, updated, cancelled, profile saved — and the failure variants.
  - No alert()/confirm() calls anywhere; the toast replaces alert() and the
    Dialog replaces confirm().

7. DATABASE / DATA STORAGE
================================================================================

Two storage mechanisms exist:

A) db.json — the json-server "database" (file on disk)
-------------------------------------------------------
  A flat JSON object whose top-level keys become REST collections:

  Collection "doctors" (10 seeded records). Doctor entity fields:
    id              number  — json-server primary key
    name            string  — e.g. "Dr. Sarah Mitchell"
    specialty       string  — "Cardiology", "Dermatology", "Pediatrics",
                              "Orthopedics", "Neurology", "Dentistry",
                              "Ophthalmology", "General Medicine",
                              "Psychiatry", "ENT"
    description     string  — free-text bio
    workingDays     string[]— e.g. ["Mon", "Tue", "Thu"]
    slots           string[]— bookable times, e.g. ["09:00","10:00",...]
    experienceYears number
    consultationFee number  — USD per visit
    rating          number  — e.g. 4.9
    phone           string
    email           string
    location        string

  Collection "appointments" (currently 1 record). Appointment entity fields:
    id          number/string — assigned by json-server on POST
    patientName string
    email       string
    phone       string
    doctorId    number        — reference to doctors.id
    date        string        — ISO date "YYYY-MM-DD"
    time        string        — "HH:MM", expected to be one of the doctor's
                               slots
    note        string        — optional, max 200 chars (client-enforced)
    status      string        — "scheduled" (set by the frontend on create;
                               "completed"/"cancelled" styles exist in
                               AppointmentStatus.jsx but nothing in the app
                               currently sets them)

  Relationship: appointments.doctorId -> doctors.id (many appointments to one
  doctor). The join is performed CLIENT-SIDE only: AppointmentsPage builds a
  doctorById map from a second GET /doctors call and passes the matching
  doctor object into AppointmentCard. There is no foreign-key enforcement —
  if an appointment references a deleted doctor, the card shows
  "Unknown doctor" and an "N/A" avatar (defensive fallback in
  AppointmentCard.jsx).

B) localStorage — the patient profile
-------------------------------------
  Zustand persist middleware stores { name, email, phone } under the key
  "medicare-patient-profile". This is per-browser only, never sent to the
  API, and not shared across devices.

No other storage (no SQL, no Supabase, no Firebase, no cookies/sessions)
is used. Authentication is NOT implemented.


================================================================================
8. APPOINTMENT SYSTEM (full CRUD workflow)
================================================================================

CREATE (BookAppointmentPage + AppointmentForm)
----------------------------------------------
  1. Route: /book (no doctor) or /book/:doctorId (doctor preselected).
  2. On mount, GET /doctors populates the doctor <select>. The patient
     name/email/phone defaults come from the Zustand profile store;
     doctorId defaults to the URL param; date/time/note default to ''.
  3. The shared AppointmentForm (React Hook Form) renders: patientName,
     email, phone, doctorId, date, time, note. Validation is described in
     section 9.
  4. The time dropdown lists the SELECTED doctor's slots (via watch
     ('doctorId')); if no doctor is selected yet, a static FALLBACK_SLOTS
     list is shown. When editing, a previously saved time is kept selectable
     even if the doctor is changed.
  5. On valid submit, onSubmit builds
       { ...values, doctorId: Number(values.doctorId), status: 'scheduled' }
     and POSTs it to /appointments.
  6. Success -> toast + navigate('/appointments'). Failure -> error toast;
     the form stays mounted with the values intact (submitting reset to
     false so the button re-enables).
  Note: double-booking is NOT prevented — the app does not check whether a
  slot is already taken (no such validation exists client or server side).

READ
----
  - AppointmentsPage: on mount, Promise.all([GET /appointments,
    GET /doctors]); builds doctorById; sorts appointments newest-first by
    string-comparing "date time"; renders AppointmentCard per appointment.
  - EditAppointmentPage: GET /appointments/:id (plus GET /doctors) to
    pre-fill the edit form.
  - A single-appointment detail page (e.g. /appointments/:id) does NOT
    exist — the card in the list is the display. Not implemented.

UPDATE / RESCHEDULE (EditAppointmentPage)
-----------------------------------------
  1. The appointment ID comes from the URL: /appointments/:id/edit,
     extracted with useParams(). The link is generated by AppointmentCard
     (`/appointments/${appointment.id}/edit`).
  2. On mount the appointment and doctors are fetched in parallel; a 404
     renders "Appointment not found" (e.g. stale id after deletion).
  3. The SAME AppointmentForm is rendered with defaultValues taken from the
     fetched appointment, so all fields are pre-populated.
  4. On submit, PUT /appointments/:id with
       { ...values, doctorId: Number(values.doctorId),
         status: appointment.status }   // status is preserved as-is
  5. Success -> toast + navigate('/appointments'); failure -> error toast.
  6. A full PUT is used (api.put), so the entire record is replaced with the
     submitted values. PATCH is not used by the app.

DELETE / CANCEL (AppointmentsPage)
----------------------------------
  1. AppointmentCard's "Cancel appointment" button (hidden when status is
     already 'cancelled') calls onCancel(appointment), which sets the page's
     cancelTarget state.
  2. That opens the confirmation Dialog: "Cancel this appointment?" showing
     doctor name, date and time, and warning that the action is permanent.
     Buttons: "Keep appointment" (dismiss) / "Yes, cancel appointment"
     (destructive). No deletion happens without this confirmation, and the
     dialog can also be dismissed with Escape or an overlay click.
  3. Confirming sets cancelling=true (button shows "Cancelling..." and is
     disabled) and issues DELETE /appointments/:id.
  4. Success -> the appointment is removed from the local list state
     (optimistic-style local update; no refetch), the dialog closes, and a
     success toast is shown. Failure -> error toast, dialog stays.
  5. "Cancel" is a hard DELETE — the record is removed from db.json. There
     is no soft-cancel (no status change to 'cancelled' via the API).


================================================================================
9. FORMS AND VALIDATION
================================================================================

All forms use React Hook Form 7 with the built-in validators (no zod/yup
schema library is used).

Shared appointment form (components/appointments/AppointmentForm.jsx)
---------------------------------------------------------------------
  Used by BOTH booking and editing; behavior is identical, only defaultValues
  and the submit handler differ.

  Inputs are UNCONTROLLED-but-registered: each field uses {...register(name,
  rules)} so React Hook Form owns the field state via refs. Validation runs
  on submit (default mode); errors appear under each field via a FieldError
  component (<p role="alert">). aria-invalid is set on invalid inputs.

  Fields and rules:
    patientName : required "Patient name is required";
                  minLength 2 -> "Name must be at least 2 characters"
    email       : required; pattern /^[\w.+-]+@[\w-]+\.[\w.-]+$/
                  -> "Enter a valid email address"
    phone       : required; pattern /^\+?[\d\s()-]{7,16}$/
                  -> "Enter a valid phone number (7-15 digits)"
    doctorId    : required + validate(value !== '')
                  -> "Please choose a doctor"
    date        : required; validate notInPast() — compares against
                  today's local ISO date -> "Date cannot be in the past";
                  the input also has min={today} (browser hint)
    time        : required + non-empty validate
                  -> "Please choose a time"
    note        : optional; maxLength 200
                  -> "Note must be 200 characters or fewer"

  Dynamic behavior: watch('doctorId') re-renders when the doctor changes so
  the time <select> shows that doctor's slots (FALLBACK_SLOTS otherwise, and
  the previously saved time is merged in when editing so it remains valid).
  dateMin is memoized once per mount (useMemo) — the "today" boundary does
  not live-update if the page stays open past midnight (minor, by design).

  Submission: <form noValidate onSubmit={handleSubmit(onSubmit)}> — native
  validation is disabled; only RHF rules apply. The submit Button is
  disabled while submitting and its label switches to "Saving...".

  Reset/default values: there is no explicit form.reset() call. Booking uses
  defaultValues built from the profile store + URL param; editing uses
  defaultValues from the fetched appointment. Both are initial values only.

Profile form (pages/ProfilePage.jsx)
------------------------------------
  Same pattern: register + handleSubmit, defaultValues from the Zustand
  store snapshot at render time. Fields: name (required, min 2), email
  (required, same pattern), phone (required, same pattern). On submit the
  store is updated and a toast is shown. No API call.

Controlled vs uncontrolled inputs
---------------------------------
  - React Hook Form fields (both forms): uncontrolled (ref-registered).
  - DoctorFilters search input and specialty select: fully CONTROLLED
    (value + onChange props from DoctorsPage state) — the doctor list
    re-filters on every keystroke.
  - The Navbar mobile menu uses local useState.

useRef usage
------------
  - DoctorFilters: searchInputRef to return focus to the search input after
    the clear (X) button empties it.
  - ToastProvider: a useRef(Map) of toast-id -> timeout handle so pending
    auto-dismiss timers can be cleared when a toast is manually closed.


================================================================================
10. STATE MANAGEMENT
================================================================================

Local React state (the default for almost everything)
-----------------------------------------------------
  Each page owns its data-fetch state: doctors/appointments arrays, loading
  and error flags, plus UI state such as search/specialty filters
  (DoctorsPage), cancelTarget/cancelling (AppointmentsPage), submitting
  (Book/Edit pages), and menuOpen (Navbar). Derived values are useMemo'd
  (filteredDoctors, specialties, doctorById, sortedAppointments).

Zustand (src/stores/useProfileStore.js)
---------------------------------------
  The single global store, created with create() + the persist middleware:

    state   : name, email, phone (strings, '' by default)
    actions : setProfile({ name, email, phone }) — nullish-coalesced to ''
    persist : localStorage key "medicare-patient-profile"

  What is stored globally: ONLY the patient's contact details. Doctors and
  appointments are deliberately NOT global — the store's own comment states
  it is "kept intentionally small".

  Why global state is used: the profile is written on the Profile page and
  read on the booking page (to pre-fill the form) — two routes that do not
  share a parent component, and the data must survive page changes and
  reloads (hence persist/localStorage).

  How components access/update it: the idiomatic selector hooks —
    const name = useProfileStore((state) => state.name)
    const setProfile = useProfileStore((state) => state.setProfile)
  used in ProfilePage (read + write) and BookAppointmentPage (read only).


================================================================================
11. ERROR / LOADING HANDLING
================================================================================

  Loading
    - Suspense + lazy per route: a skeleton "page" fallback while the chunk
      downloads (router.jsx PageFallback).
    - Per-page skeleton UIs while data fetches (DoctorListSkeleton with 6
      card skeletons, AppointmentsSkeleton with 3, FormSkeleton/EditSkeleton
      with field skeletons). Buttons show "Saving..."/"Cancelling..." while
      a mutation is in flight.

  API errors (fetch)
    - Generic: ErrorAlert banner with the message "Please check that the API
      server is running, then try again." plus a "Try again" button that
      re-runs the loader. Retrying re-enters the loading state.
    - Network/JSON details from the error object are NOT surfaced to the
      user (fixed friendly messages instead).

  Invalid IDs (404)
    - DoctorDetailsPage and EditAppointmentPage check
      err.response?.status === 404 and render a dedicated "not found"
      variant with a back link, distinct from network errors.
    - An appointment whose doctorId no longer resolves renders
      "Unknown doctor" with an "N/A" avatar instead of crashing.

  404 pages (unknown routes)
    - Catch-all "*" route renders NotFoundPage ("404 — Page not found") with
      links to /, /appointments and /book.

  Empty data
    - Doctors: dashed-border empty state with a SearchX icon when
      search/filter yields nothing.
    - Appointments: empty state with a CalendarPlus icon and a
      "Book your first appointment" call-to-action.

  Successful operations
    - Toasts (success type, 4 s auto-dismiss): appointment booked /
      updated / cancelled, profile saved.

  Form validation errors
    - Inline per-field <p role="alert"> messages in destructive color,
      aria-invalid on the inputs; the form simply is not submitted until
      valid. No toast for validation errors.

  Not implemented
    - Error boundaries beyond Suspense; global HTTP interceptors for
      auth/retry (no axios interceptors are configured); offline handling.

13. COMPLETE USER FLOW (typical journey, as implemented)
================================================================================

  1.  User opens the app at "/" .
  2.  DoctorsPage mounts and calls getDoctors() -> GET /api/doctors
      (Vite proxy -> http://localhost:3001/doctors) while a skeleton list
      shows.
  3.  The 10 doctors from db.json render as DoctorCards. The user types in
      the search box (controlled input filters by name) and/or picks a
      specialty — the list re-filters instantly, client-side.
  4.  User clicks a doctor card -> /doctors/:id . DoctorDetailsPage fetches
      GET /doctors/:id and shows the full profile: experience, working days,
      phone, email, location, available time slots, consultation fee.
  5.  User clicks "Book Appointment" -> /book/:doctorId .
  6.  BookAppointmentPage fetches the doctor list and builds the form. If the
      user previously saved a profile (name/email/phone in localStorage via
      Zustand), those fields are pre-filled; the doctor from the URL is
      preselected, and the time dropdown shows that doctor's slots.
  7.  User fills/adjusts the fields. React Hook Form validates (required
      fields, email/phone patterns, date not in the past, note <= 200 chars)
      with inline error messages.
  8.  On submit: POST /api/appointments with the values, doctorId coerced to
      a number, and status "scheduled". json-server appends the record to
      db.json (assigning an id) and returns it.
  9.  A success toast appears; the app navigates to /appointments .
  10. AppointmentsPage fetches appointments AND doctors, joins them
      client-side, sorts newest-first, and renders AppointmentCards with the
      doctor's name/specialty and a "scheduled" status badge.
  11. RESCHEDULE: the user clicks "Edit / Reschedule" ->
      /appointments/:id/edit . The appointment is fetched (GET
      /appointments/:id) and the same form is pre-filled. Submitting sends
      PUT /appointments/:id (full replacement, status preserved), shows a
      toast and returns to /appointments (which re-fetches).
  12. CANCEL: the user clicks "Cancel appointment"; a confirmation Dialog
      shows the doctor/date/time. Confirming sends DELETE
      /appointments/:id; on success the card disappears (removed from local
      state), the dialog closes, and a success toast shows.
  13. PROFILE (optional, at any point): on /profile the user saves
      name/email/phone into the Zustand store (persisted to localStorage);
      the next booking form is pre-filled with those details.

15. HOW TO RUN THE SYSTEM
================================================================================

Required software
-----------------
  - Node.js (a current LTS version — Vite 8 requires Node 20.19+ / 22.12+)
  - npm (bundled with Node)
  - A modern browser

Setup
-----
  1. Install dependencies:
        npm install
  2. (Optional) configure the API base URL:
        cp .env.example .env
     The shipped default is VITE_API_URL=/api (use the Vite dev proxy).
     No other environment variables exist.

Run (two terminals)
-------------------
  Terminal 1 — the REST API (json-server on port 3001):
        npm run api
  Terminal 2 — the React frontend (Vite dev server):
        npm run dev
  Then open the URL Vite prints (typically http://localhost:5173).

  How they connect: the app requests /api/*; the Vite dev server proxies
  them to http://localhost:3001 with the /api prefix stripped
  (vite.config.js) — no CORS configuration needed. If json-server is not
  running, every page shows its error state with a "Try again" button.

Production build / local preview
--------------------------------
        npm run build      # outputs static assets to dist/
        npm run preview    # serves dist/ locally
  NOTE: `npm run preview` serves only the frontend; the /api proxy is a
  DEV-server feature and is not active in preview. A production build must
  point VITE_API_URL at a reachable, CORS-enabled API host.

Lint
----
        npm run lint       # oxlint

Other notes
-----------
  - There are no tests (no test script, no test framework). Not implemented.
  - Data reset: stop json-server and edit/revert db.json; it is a plain
    file, and every POST/PUT/DELETE mutates it persistently.


================================================================================
16. DEPLOYMENT
================================================================================

  Can the project be deployed as-is?  The FRONTEND can be deployed as static
  files (npm run build -> dist/), but the application would NOT be functional
  against its own data source, because:

  1. The backend is json-server reading a local db.json file, intended for
     development only. It is not deployed anywhere, has no authentication,
     no validation, and no persistence guarantees suitable for production.
  2. In dev, the frontend relies on the Vite dev proxy (/api ->
     localhost:3001). That proxy does not exist in a deployed static build,
     so requests to the relative "/api" base URL would 404 on the hosting
     provider.
  3. For a fully functional public deployment you would need:
       a hosted REST API implementing at least the used endpoints
       (GET/POST/PUT/DELETE on /doctors and /appointments),
       VITE_API_URL set to that API's public URL at build time,
       and CORS enabled on that API (or a same-origin reverse proxy).
  4. Because createBrowserRouter uses the History API, the static host must
     be configured to rewrite all paths to index.html so deep links like
     /doctors/3 or /appointments/1/edit work on a cold load.
  5. No environment besides VITE_API_URL is expected at runtime; the patient
     profile lives in each visitor's own localStorage (per-browser only).

  The README's deployment notes agree with this assessment: the project has
  not been deployed and runs locally via npm run dev + npm run api.

18. TECHNICAL SUMMARY
================================================================================

  What is the frontend?   A React 19 single-page application built with
                          Vite 8, using functional components + hooks only,
                          with the React Compiler enabled. Styling is
                          Tailwind CSS 4 with hand-written shadcn/ui-style
                          primitives and lucide-react icons.

  What is the backend?    json-server — a MOCK REST API / development
                          server, NOT a custom backend. No Node/Express,
                          no ASP.NET, no other server code exists in the
                          repository.

  What is the API?        REST endpoints auto-generated by json-server from
                          db.json on http://localhost:3001. The app uses:
                          GET /doctors, GET /doctors/:id, GET /appointments,
                          GET /appointments/:id, POST /appointments,
                          PUT /appointments/:id, DELETE /appointments/:id.

  Where is the data stored?
                          (a) db.json file at the project root (doctors and
                          appointments, mutated by json-server), and
                          (b) browser localStorage for the patient profile
                          (Zustand persist, key "medicare-patient-profile").
                          No SQL/NoSQL/cloud database.

  How does frontend/backend communication work?
                          All HTTP goes through one Axios instance
                          (src/services/api.js, baseURL VITE_API_URL,
                          default "/api"). In development the Vite dev
                          server proxies /api/* to http://localhost:3001,
                          stripping the prefix, which avoids CORS. Response
                          bodies are unwrapped (.data) before reaching pages.

  How is state managed?  Component-local useState/useMemo for all server
                          data and UI state; one small global Zustand store
                          (persisted) for the patient contact profile, read
                          by the booking form and written by the profile
                          page. No Redux, no Context for app data (Context
                          only inside the Toast provider).

  How are forms handled? React Hook Form 7 with uncontrolled registered
                          inputs ({...register(name, rules)}), defaultValues
                          from the store/URL/fetched record, validation via
                          required/minLength/maxLength/pattern/validate,
                          inline per-field error messages, noValidate forms,
                          disabled submit buttons while saving. The
                          doctor-search filter, by contrast, is a controlled
                          input.

  How is CRUD implemented?
                          CREATE : POST /appointments from
                                   BookAppointmentPage (status "scheduled").
                          READ   : GET on page mount (list pages) / by id
                                   (detail and edit pages); doctor-appointment
                                   joins and sorting done client-side.
                          UPDATE : PUT /appointments/:id from
                                   EditAppointmentPage (id from the URL
                                   param :id, status preserved).
                          DELETE : DELETE /appointments/:id from
                                   AppointmentsPage behind a confirmation
                                   Dialog, followed by a local state update.
                          All mutations report via toasts; fetch failures
                          show retryable error alerts; 404s get dedicated
                          "not found" views.

  Main technologies:      React 19, Vite 8, React Router DOM 7, Zustand 5
                          (+ persist), Axios, React Hook Form 7, Tailwind
                          CSS 4 (+ cva/clsx/tailwind-merge, lucide-react),
                          json-server 0.17, oxlint.

  Known limitations (as found in the code):
                          - Mock backend only; not deployable as a working
                            public app without a hosted API.
                          - No authentication / multi-user support; a single
                            implicit patient.
                          - No double-booking prevention (slot availability
                            is not checked).
                          - All filtering/sorting is client-side.
                          - No automated tests.
                          - No axios interceptors / no retry logic for
                            mutations.
                          - status values "completed"/"cancelled" have UI
                            styles but nothing sets them via the API.
